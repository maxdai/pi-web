## 差异分类

- **by-design**：`/ctx-status`、`/aft-status` 等扩展面板——原生引擎的桥接扩展会渲染面板，SDK 宿主对这些命令强制 `hasUI:false` 走文本 fallback（见 §15.11）。
- **需人工判断**：其余差异；若属回归则应先修复再进入阶段 E。

差异项数：6 / 16

## 差异逐项解释（人工判定）

| 差异 | 判定 | 依据 |
|---|---|---|
| 命令数 27 vs 28：仅 B（native）多出 **`pi-web:reload`** | **by-design，但实现细节外露（待定）** | 原生引擎没有 RPC 级 reload 通道，reload 必须经注入扩展的命令完成，桥接因此注册该命令；它同时出现在 `/` 菜单。SDK 宿主直接用 `reload` 消息帧，无需命令。**待定**：是否把它从 `/` 菜单隐藏，或保留为显式功能 |
| 工具数 21 vs 20：A 有 **`codemode`**，B 无 | **已知差异（Pi 启动 vs reload 的 loadout），非引擎差异** | 本轮复测：同一原生进程执行 `/pi-web:reload` 后 state 帧序列 **20 → 21**，服务端日志 `bridge event: {"type":"reloaded"}`。§16 第 22 项已记录同一结论（曾误判为"SDK 注入内置扩展"，已被该实验推翻） |
| `panelGeometry` 能力位 false vs true | **by-design** | 原生引擎支持前端上报面板几何（§15.11 / §15.12）；SDK 宿主不支持该帧，前端有能力位门控 |
| `/ctx-status` 表现 `notify(title=/ctx-status)` vs `panel(40 行)` | **by-design** | SDK 宿主对 magic-context / aft-pi 强制 `hasUI:false` → 文本 fallback；原生引擎的桥接扩展能渲染 TUI 面板（§15.11） |
| 帧类型多出 `entry_appended`（仅 A） | **by-design（随上一条）** | SDK 的文本 fallback 经 appendEntry 落到聊天流；原生引擎走面板 |
| 其余 11 项（piWebVersion、pi 版本、模型、thinking、命令交集、扩展名单、scoped 模型数、可选模型数、stats 字段、usage 顶层字段、会话数） | **一致 ✅** | — |

## 结论

- **无"需修复的回归"**：6 项差异中 5 项为 by-design 或已记录的 Pi 启动/ reload loadout 差异，1 项（`pi-web:reload` 外露）属实现细节。
- 满足 §15.13 步骤 1 的"有记录的两引擎 A/B"要求，可作为删除 SDK 引擎前的对照证据。
- 两个**待定项**（不阻塞阶段 E）：
  1. `pi-web:reload` 是否从 `/` 菜单隐藏（或保留为显式功能）；
  2. 原生引擎是否在启动后**自动 reload 一次**，以对齐 SDK/TUI 的工具 loadout（当前启动时缺 `codemode`，执行一次 reload 即补齐）。

_生成方式：`node tools/ab-compare.mjs --snapshot <url> --json <file>` 分步抓取（同一会话顺序执行，避免两个 pi 同时写同一会话文件），再 `--diff` 对比。_
